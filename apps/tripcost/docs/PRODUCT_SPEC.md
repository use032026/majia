## 1. 产品概述

### 1.1 名称与视觉方向

- 正式中文名：RhinoSmart
- 正式英文名：RhinoSmart
- 项目代号：TripCost（仅保留用于工程路径与内部兼容标识，不作为用户可见名称）
- App Icon：使用 `assets/branding/rhinosmart_app_icon.png` 中已确认的蓝底白色标志。
- 暂定 Slogan：看懂价格，选对支付，控制旅行预算。
- 视觉方向：接近原生 iOS 的清晰、克制、内容优先风格。
- Flutter 主界面优先使用 Cupertino 语义和符合 iOS 习惯的导航、弹窗、表单、间距与动效。
- WidgetKit 扩展使用 SwiftUI，跟随系统浅色/深色、动态字体和辅助功能设置。

正式名称与 App Icon 已确认；正式上架前仍需完成主色、商标、App Store 重名和域名检查。业务代码、路由、数据库和原生 Target 不应硬编码项目代号，以降低后续改名成本。

### 1.2 产品定位

本产品不是单纯的汇率换算器，而是一款面向全球出境旅行者的“真实消费成本助手”。首版界面支持简体中文和英文，不限制用户所在地区或目的地。

普通汇率产品主要回答：

> 10000 日元按参考汇率等于多少人民币？

本产品需要进一步回答：

1. 这件商品按当前参考汇率约合多少本位币？
2. 使用现金、信用卡或其他支付方式，预计最终成本是多少？
3. 商户提供的本币结算（DCC）是否明显高于参考价格？
4. 这笔消费计入行程后，预算还剩多少？

### 1.3 核心价值

核心使用闭环：

```text
看到当地价格
  -> 扫描或输入金额
  -> 换算为本位币
  -> 比较不同支付方式的预计成本
  -> 判断如何付款
  -> 记录消费并更新旅行预算
```

### 1.4 产品原则

1. **决策优先**：不仅展示汇率，还要帮助用户选择支付方式。
2. **结果诚实**：所有非实际账单金额均标记为“参考”或“预计”。
3. **离线可用**：无网络时仍能换算、扫描、记账和查看预算。
4. **隐私优先**：无需注册，不收集银行卡号，票据默认仅保存在本地。
5. **低操作成本**：打开 App 后应能立即输入或扫描价格。
6. **历史可追溯**：消费记录保存当时的汇率快照，不能随最新汇率变化。

## 2. 目标用户与场景

### 2.1 主要用户

- 全球出境自由行游客（首版提供简体中文和英文界面）
- 留学生及短期交换生
- 经常跨境出差的商务用户
- 需要比较现金和银行卡成本的境外消费者
- 希望使用本位币管理旅行预算的用户

### 2.2 高频场景

#### 场景 A：查看商品实际成本

用户在日本商店看到 JPY 12,800 的商品，扫描价签后查看人民币参考金额和不同支付方式的预计成本。

#### 场景 B：检查 DCC

POS 机让用户选择“JPY 12,800”或“CNY 648”，用户输入两个报价，App 计算商户人民币报价相对参考换算的额外成本。

#### 场景 C：控制旅行预算

用户为东京七日旅行设置 CNY 8,000 的总预算。每次消费后，App 更新已消费金额、剩余预算和剩余每日可用金额。

#### 场景 D：离线使用

用户在无网络环境下，使用最近缓存汇率和本地 OCR 完成换算与记账，并清楚看到汇率的缓存时间。

#### 场景 E：实际账单校准

信用卡交易正式入账后，用户补录人民币实际扣款金额，App 反推出该支付方式本次交易的综合加价率，改善后续估算。

## 5. 页面与功能说明

### 5.1 启动与首次引导

引导最多三屏：

1. 扫描价签、菜单和账单，快速理解当地价格。
2. 结合手续费比较不同支付方式的预计实际成本。
3. 将消费加入行程，持续跟踪旅行预算。

初始化项目：

- 选择默认本位币：优先根据系统地区建议；无法判断时，简体中文界面建议 CNY，英文界面建议 USD，但始终允许用户修改。
- 选择目的地和当地货币，可跳过。
- 设置行程预算，可跳过。
- 配置支付方式，可跳过。
- 下载离线汇率，可跳过。

验收要求：

- 用户未创建行程也能直接进入首页换算。
- 相机、相册和通知权限只能在功能实际需要时请求。
- 不得要求登录或填写手机号、邮箱。

### 5.2 首页 / 快速换算

首页组成：

1. 当前行程摘要：地点、行程天数、预算进度。
2. 金额输入区：交易币种、金额、本位币结果。
3. 汇率信息：数据源、更新时间、在线/缓存/手动状态。
4. 支付方式比较：显示成本最低的若干支付方式。
5. 快捷动作：检查 DCC、保存消费、打开扫描。
6. 最近消费记录。

金额输入要求：

- 支持数字、小数点、加、减、乘、除和括号。
- 示例：`1200 * 3 + 500`。
- 支持切换交易币种和本位币。
- 支持交换两种币种。
- 支持收藏常用币种。
- 输入过程中实时更新结果。

状态要求：

- 在线汇率显示更新时间。
- 离线汇率明确显示“缓存于 YYYY-MM-DD HH:mm”。
- 手动汇率明确显示“当前使用手动汇率”。
- 汇率不可用时仍允许用户输入手动汇率。

### 5.3 相机 / 相册识价

支持对象：

- 商品价签
- 餐厅菜单
- 购物小票
- 酒店账单
- POS 机画面
- 网页或聊天截图中的价格

识别流程：

```text
选择相机或相册
  -> 本地 OCR 识别候选金额
  -> 用户选择一个或多个金额
  -> App 尝试推断币种
  -> 用户确认金额和币种
  -> 进入支付方式比较
```

交互要求：

- 使用识别框标记所有候选金额。
- 多个价格可单选或多选求和。
- 用户可手动修改识别数字和币种。
- 应尽量排除日期、编号、电话号码等误识别内容。
- 无法识别时提供手动输入，不阻断流程。
- OCR 默认在设备本地完成，不上传原图。

### 5.4 消费成本结果

展示内容：

- 交易币种原始金额
- 市场参考换算金额
- 各支付方式预计成本
- 手续费、固定费用和返现拆分
- 推荐的最低预计成本支付方式
- 与其他支付方式的预计差额
- 汇率来源和更新时间
- 估算免责声明

允许编辑：

- 支付方式
- 消费日期
- 分类
- 商户或项目名称
- 税费
- 小费
- 优惠金额
- 人数
- 是否计入行程预算
- 备注和票据图片

结果不得使用“保证”“准确到账”“绝对最优”等确定性表述。

### 5.5 支付方式管理

支持类型：

- 信用卡
- 借记卡
- 现金
- 电子钱包
- 自定义支付方式

支付方式字段：

- 自定义名称
- 类型
- 卡组织：Visa、Mastercard、银联、JCB、其他、未知
- 账单币种
- 外币转换费率
- 境外交易费率
- 汇率额外加价率
- 固定手续费
- 返现比例
- 最低/最高手续费（可选）
- 适用交易类型：消费、ATM 或全部
- 备注
- 数据来源及最后确认时间（预设规则使用）

内置通用模板：

- 无外币手续费卡
- 1% 手续费卡
- 1.5% 手续费卡
- 2% 手续费卡
- 银联人民币结算卡
- 现金兑换
- 完全自定义

约束：

- 不保存银行卡号、有效期、CVV 或身份证信息。
- 银行及卡产品规则只能在存在官方来源时作为预设。
- 所有预设均允许用户修改，并提示银行政策可能变化。

### 5.6 DCC 检查

输入：

- 当地货币金额
- 商户提供的本位币金额
- 可选支付方式

输出：

- 商户隐含汇率
- 市场或卡组织参考汇率
- 按参考汇率计算的金额
- DCC 报价额外金额
- DCC 报价额外百分比
- 使用当地货币结算的一般性提示

示例：

```text
当地货币金额：JPY 12,800
商户人民币报价：CNY 648.00
参考换算金额：CNY 612.36
额外成本：CNY 35.64 / 5.82%
```

提示文案需保留不确定性：

> 商户提供的本位币报价比当前参考换算高约 5.82%。通常选择当地货币结算更透明，但最终入账金额仍取决于发卡机构。

### 5.7 行程列表

分组：

- 进行中
- 即将开始
- 历史行程

每张行程卡显示：

- 行程名称和目的地
- 日期范围
- 当地货币
- 总预算、已消费金额和使用比例
- 离线包状态

操作：

- 新建
- 编辑
- 复制配置
- 归档
- 导出
- 删除（需要二次确认）

### 5.8 新建/编辑行程

字段：

- 行程名称
- 一个或多个国家/地区
- 开始和结束日期
- 本位币
- 一个或多个当地货币
- 总预算
- 每日预算（可自动计算）
- 同行人数
- 默认支付方式
- 是否下载离线旅行包

目的地仅用于推荐币种，不应强制请求定位权限。

### 5.9 行程仪表盘

展示：

- 总预算、已消费和剩余预算
- 当前是第几天/总天数
- 当前日均消费
- 剩余每日可用金额
- 分类占比
- 支付方式占比
- 当地货币和本位币双金额
- 最近消费
- 快速扫描和手动记账入口

计算：

```text
剩余预算 = 总预算 - 已确认消费 - 计入预算的预计消费
剩余每日可用 = 剩余预算 / 剩余行程天数
当前日均 = 累计消费 / 已进行天数
```

已确认金额优先于预计金额，避免重复计入。

### 5.10 消费账本

查看方式：

- 时间线
- 日历
- 分类统计

筛选：

- 行程
- 日期
- 分类
- 交易币种
- 支付方式
- 金额范围
- 预计/已确认状态

每条消费记录保存：

- 原始金额与交易币种
- 当时的参考汇率快照
- 预计本位币成本
- 实际入账金额（可选）
- 支付方式及当时的费用规则快照
- 行程、分类和日期
- 商户/项目名称
- 备注
- 票据图片本地路径
- 汇率来源和更新时间

### 5.11 实际入账校准

用户补录实际入账金额后，App 计算本次综合加价：

```text
综合加价率 = 实际入账金额 / 同期参考换算金额 - 1
```

显示：

- 原预计金额
- 实际入账金额
- 差额和差额比例
- 当前支付方式最近若干笔交易的综合加价区间

规则：

- 不应根据单笔交易自动修改支付方式参数。
- 至少积累 3 笔可比较数据后，再建议用户更新默认加价率。
- 更新前必须由用户确认。
- 历史交易保留原费用规则快照，不随支付方式配置变化。
- 原交易的实际入账金额表示已经发生的入账事实；退款作为关联原交易的独立负向记录保存，不把原实际金额改成零。
- 无退款、部分退款、全部退款和异常退款状态由原实际金额与累计退款实时推导，不保存第二份可漂移的聚合状态。
- 待入账记录只允许补录实际金额或撤销；已入账记录只允许退款、冲正或受控更正，不允许直接撤销。
- 更正原交易金额后，累计退款不得超过新的实际入账金额；更正退款金额后也必须重新校验累计上限。

### 5.12 行程总结与导出

行程结束后展示：

- 总支出和预算结余
- 日均支出
- 最大单笔消费
- 分类占比
- 支付方式占比
- 预计与实际金额差异
- 最常使用的币种
- 可用数据充足时的综合加价统计

导出形式：

- CSV：消费明细
- PDF：行程汇总和明细
- 图片：适合分享的总结卡片

## 6. 汇率与手续费数据策略

### 6.1 数据分层

#### 第一层：市场参考汇率

首版选用 **Frankfurter v2 公共 API**（`https://api.frankfurter.dev/v2`）作为市场参考汇率主数据源，用于：

- 普通换算
- 现金参考成本
- 行程预算
- DCC 比较基准

必须记录：

- 数据源
- 汇率日期/时间
- 获取时间
- 基础币种
- 是否为缓存或手动汇率

Frankfurter 使用约束：

- 无需 API Key，首版直接使用托管公共 API，不自建汇率后端。
- 使用 v2 API，不使用已被 v2 取代的 v1 API。
- 数据来自中央银行等公开机构，属于每日参考汇率，不是实时交易报价。
- UI 使用“最新参考汇率”，不得使用“实时汇率”文案。
- 支持币种以 `/v2/currencies` 的实际返回为准，不在客户端硬编码“全球所有币种”。
- 上架前逐项复核实际使用 provider 的数据条款和必要署名；Frankfurter 官方也要求查看各 provider 的底层数据条款。
- 批量刷新优先使用 `/v2/rates`；单一货币对按需使用 `/v2/rate/{base}/{quote}`。
- 保存响应中的汇率日期，并与设备请求时间分开记录。
- 历史消费优先查询交易日数据；非工作日由数据源返回最近有效参考数据时，界面仍展示实际汇率日期。
- 公共服务不承诺业务 SLA，因此离线缓存、手动汇率和请求失败退避是首版必备能力。

Frankfurter 推荐结论：适合作为首版市场参考源，原因是无需密钥、覆盖范围广、支持历史数据且可自托管；但不能替代 Visa、Mastercard、银联或发卡行的实际清算汇率。后续若公共服务稳定性不足，可以自托管同一开源服务，保持客户端协议和业务语义基本不变。

#### 第二层：卡组织参考汇率

后续可评估接入 Visa、Mastercard、银联或 JCB 的官方渠道。第一版不能假设这些接口均可免费直接用于生产。

注意：

- Visa 提供官方 Foreign Exchange Rates API，但生产环境需要申请和认证。
- Mastercard 提供官方汇率计算器，但银行手续费由调用者提供。
- 银联提供官方汇率查询，但明确排除发卡行附加费用。
- 不通过抓取网页的方式构建生产依赖。

#### 第三层：发卡行手续费

目前不存在覆盖全部发卡行和卡产品、长期可靠的统一开放 API。采用以下组合：

1. 用户自行配置。
2. App 内置通用手续费模板。
3. 通过实际入账金额进行本地校准。

V1.0 不提供具体银行或卡产品预设，不维护银行规则库。数据模型保留以下字段，供未来版本引入官方预设时使用：

- 生效日期
- 官方来源 URL
- 最后人工确认时间
- 适用地区、币种和交易类型
- 已失效状态

### 6.2 汇率优先级

建议优先级：

```text
用户指定手动汇率
  > 可用的卡组织参考汇率
  > 最新市场参考汇率
  > 缓存市场参考汇率
```

每次计算必须保存实际使用的汇率及其来源。

### 6.3 刷新和缓存

- App 冷启动时检查缓存是否过期。
- 同一基础币种的一组货币尽量批量获取，避免逐货币对调用。
- 应使用缓存、请求去重和失败退避，避免 API 配额失控。
- 周末或数据源未更新时继续使用最后可用数据，并显示原始更新时间。
- 离线包至少保存目的地货币和本位币所需的最新汇率。

## 7. 计算规则

### 7.1 基础换算

```text
参考换算金额 = 交易金额 * 交易币种到本位币汇率
```

内部计算使用高精度十进制类型，不使用二进制浮点数直接处理金额。页面展示时才按币种小数位舍入。

### 7.2 支付方式预计成本

通用模型：

```text
基础换算金额 = 交易金额 * 使用汇率
汇率加价金额 = 基础换算金额 * 汇率额外加价率
外币转换费 = (基础换算金额 + 汇率加价金额) * 外币转换费率
境外交易费 = (基础换算金额 + 汇率加价金额) * 境外交易费率
手续费小计 = 按最低/最高限制修正后的各项费用 + 固定手续费
预计返现 = 按支付方式规则计算的返现金额
预计实际成本 = 基础换算金额 + 汇率加价金额 + 手续费小计 - 预计返现
```

不同银行可能采用不同计算顺序，首版结果必须作为估算。模型需要保留扩展能力，后续允许为特定预设配置计算顺序。

### 7.3 现金成本

现金成本应优先使用用户实际购汇成本：

```text
现金实际汇率 = 支付的本位币金额 / 获得的外币金额
现金消费成本 = 外币消费金额 * 现金实际汇率
```

用户未填写时，才使用市场参考汇率并标记为估算。

### 7.4 DCC 计算

```text
商户隐含汇率 = 商户本位币报价 / 当地货币金额
参考换算金额 = 当地货币金额 * 参考汇率
DCC 额外金额 = 商户本位币报价 - 参考换算金额
DCC 额外比例 = 商户本位币报价 / 参考换算金额 - 1
```

### 7.5 金额展示

- CNY、USD、EUR 等默认显示 2 位小数。
- JPY、KRW 等零小数币种的原币金额默认不显示小数。
- 内部保留足够精度，避免多次换算造成累计误差。
- 预计结果可显示合理区间，不能通过过多小数制造虚假精确感。

## 9. 离线、同步与隐私

### 9.1 离线能力

无网络时仍可使用：

- 缓存汇率换算
- 手动汇率
- 本地 OCR
- 支付方式比较
- DCC 计算
- 行程和预算
- 消费记账
- 历史记录查询

必须展示缓存汇率的原始更新时间。

### 9.2 本地存储

- 行程、消费、支付方式和汇率快照使用 Drift 管理的 SQLite 本地数据库。
- 金额使用十进制或最小货币单位保存，避免浮点误差。
- 票据图片使用应用私有目录，并支持单独清理。
- 删除行程前提示是否同时删除其票据图片。
- WidgetKit 不直接打开或迁移 Flutter 主数据库；主 App 将小组件需要的最小只读快照写入 App Group 共享容器。

### 9.3 云同步

iCloud 同步纳入 V1.0，采用“本地数据库为主、CloudKit 私有数据库为同步层”的 offline-first 方案：

- Flutter 业务层继续读写 Drift/SQLite，不把 SQLite 文件直接放入 iCloud Drive。
- Swift 原生 CloudKit 服务通过 Pigeon 接收结构化增量记录并返回远端变更。
- 首版同步行程、消费、支付方式、汇率快照引用和用户设置。
- 首版不跨设备同步票据原图；图片保留在当前设备并在界面中明确说明。后续可使用 `CKAsset` 扩展。
- 每条可同步记录包含稳定 UUID、`updatedAt`、`deletedAt` 和同步版本字段。
- 删除采用墓碑记录，避免另一台设备将已删除数据重新上传。
- 默认冲突规则为字段级无法合并时“最后修改时间优先”；涉及实际入账金额的冲突必须保留冲突提示，不能静默覆盖。
- 未登录 iCloud、CloudKit 不可用、网络失败或配额异常时，本地功能保持完整可用。
- 用户可关闭同步；关闭同步不删除本地数据。
- 设置页显示同步开关、当前状态、最近成功时间、失败原因和“立即同步”。

### 9.4 隐私要求

- 不要求账户注册。
- 不保存完整卡号、CVV、身份证或银行登录信息。
- OCR 默认本地执行。
- 未经明确授权不上传票据或消费数据。
- 定位权限不是核心依赖，目的地由用户选择。
- 隐私政策准确声明所用汇率服务和第三方 SDK 的数据行为。

### 10.4 Flutter 与原生通信契约

使用 Pigeon 定义以下边界：

```text

  recognizeImage(path, preferredLanguages)
  supportedRecognitionLanguages()

CloudSyncApi
  accountStatus()
  pushChanges(records, cursor)
  pullChanges(cursor)

SharedSnapshotApi
  writeWidgetSnapshot(snapshot)
  clearWidgetSnapshot()

WidgetControlApi
  reloadTimelines()
```

OCR 返回候选文本、置信度和归一化坐标框，由 Dart 层完成币种符号、金额格式、多价格选择和业务纠错。Swift 层不包含旅行预算或支付费用计算逻辑。

Widget 共享规则：

- 使用 App Group 的 `UserDefaults(suiteName:)` 或原子 JSON 文件保存小型快照。
- 快照只包含选中的货币对、换算金额、汇率日期、缓存状态和目标行程预算摘要。
- Widget 不直接依赖 Flutter Engine，也不直接访问 Drift 数据库。
- 主 App 写入成功后调用 `WidgetCenter.reloadTimelines`。
- iOS 15 使用主屏幕 Widget；iOS 16+ 可按条件增加锁屏样式，但不是 iOS 15 的验收项。

### 10.5 OCR 原生实现约束

- 使用 `VNRecognizeTextRequest`，相机实时预览优先走快速模式，确认图片走准确模式。
- 按设备能力查询支持的识别语言，不假设所有 iOS 15 设备支持相同语言集合。
- 简体中文界面优先请求简体中文和英文；英文界面优先请求英文，并允许用户选择其他可用识别语言。
- OCR 仅负责识别文本和位置；金额解析、千分位/小数点歧义及货币符号归一化由 Dart 层统一处理。
- 所有图片默认在设备端处理，不因 OCR 功能上传到服务端。

## 11. 异常与边界状态

必须覆盖：

- 首次启动无网络且无缓存汇率
- 汇率 API 超时、限流或返回缺失币种
- 汇率数据长时间未更新
- OCR 未识别到金额
- OCR 将日期或编号误识别为金额
- 用户扫描到多个币种
- 用户未配置任何支付方式
- 行程预算为零或未设置
- 实际入账金额早于或晚于消费日期数日
- 退款、撤销、部分退款
- 小费或押金在后续追加
- 相同消费被重复保存
- 票据图片被系统清理或文件丢失
- 用户切换本位币后历史记录的展示
- 删除支付方式时仍有历史消费引用
- 不支持或已废止的 ISO 货币代码

历史记录引用支付方式和汇率快照，删除或修改当前配置不得破坏历史计算。

## 13. V1.0 核心验收标准

### 13.1 快速换算

- 打开 App 后两次操作内可以开始输入金额。
- 输入表达式后能正确计算并换算。
- 结果明确标记币种、汇率来源和更新时间。
- 无网络时使用缓存，且有明显的过期状态。

### 13.2 OCR

- 相机和相册均可进入识别流程。
- 多候选金额可由用户选择和修正。
- OCR 失败后可无缝切换手动输入。
- 原图默认不上传。

### 13.3 支付成本

- 用户至少可建立现金和一个自定义信用卡支付方式。
- 同一笔消费能比较至少两个支付方式。
- 费用明细可解释最终预计金额的构成。
- 所有估算结果均有非确定性提示。

### 13.4 行程与账本

- 消费保存后立即更新行程预算。
- 历史消费保存当时汇率和费用规则快照。
- 用户可补录实际入账并查看预计差额。
- 修改当前支付规则不会改变历史消费结果。

### 13.5 数据可靠性

- 金额计算不使用普通浮点数作为最终账务精度。
- 所有删除操作有合理确认和关联数据处理。
- 汇率服务失败不会造成已有账本不可用。
- 可导出用户的消费明细。

### 13.6 iCloud 同步

- 未登录 iCloud 或同步失败时，所有本地核心功能仍可使用。
- 两台设备能同步行程、消费、支付方式和设置的新增及修改。
- 一台设备删除记录后，不会被另一台设备重新创建。
- 实际入账金额发生冲突时向用户提示，不静默丢弃任一值。
- 设置页能看到同步状态和最近成功时间。
- 票据原图不在 V1.0 同步范围内，界面有明确说明。

### 13.7 Widget

- iOS 15 主屏幕可添加 Widget。
- Widget 在不启动 Flutter Engine 的情况下展示主 App 写入的共享快照。
- Widget 展示汇率日期和缓存状态，不能把过期数据伪装为最新数据。
- 主 App 更新选中货币或行程摘要后能请求刷新 Widget 时间线。
- iOS 15 不以锁屏 Widget 或 App Intents 作为验收要求。

### 13.8 国际化与导出

- 简体中文和英文界面均不存在未替换的开发键名。
